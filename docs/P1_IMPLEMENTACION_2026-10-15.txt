1. QUÉ CAMBIÓ
REP-01. La materialización valida el formato completo antes de conectar JDBC o publicar. El adaptador admite únicamente XML legado con raíz mapping e hijos rr:sqlQuery SELECT; rechaza explícitamente R2RML general, estructuras no soportadas y entidades externas. Las consultas terminan y todos los recursos JDBC se cierran antes de publicar. Un resultado vacío devuelve EMPTY/200, conserva el grafo y los metadatos, y la UI muestra un aviso. Los mapeos no admitidos producen 422 estructurado; el caso soportado continúa publicando las triples previstas.
Además, una publicación conserva un snapshot previo y puede compensarse ante un error posterior o rollback confirmado. La restauración usa una sola actualización SPARQL condicionada a que el grafo siga siendo exactamente el publicado por esa operación. No pisa contenido distinto de otro escritor ni multiplica nodos anónimos del snapshot. Un recibo con UUID identifica restauración, cambio ajeno, fallo de compensación o resultado transaccional desconocido.

REP-02. El Wizard ejecuta los IDs de reglas registrados que se seleccionaron para esa sesión. No utiliza en su lugar la activación global, no crea reglas globales y no modifica su estado. Una regla globalmente inactiva puede seleccionarse localmente; la UI explica esa política. La selección vacía significa OWL sin SWRL. Se rechazan IDs desconocidos, repetidos o sin identificador ejecutable, y cambiar la selección invalida la verificación anterior. API y UI cotejan selección y recibo efectivo de IDs/nombres. La sesión guarda el snapshot exacto de definiciones RDF y su SHA256; la UI ofrece esa huella en un detalle de trazabilidad. Identifica bytes suministrados, no una versión semántica ni una canonicalización RDF. La finalización vuelve a verificar antes de publicar.

REP-03. Cada carga tiene propietario persistente, UUID, estado y grafos propios. Los temporales no entran al catálogo de módulos permanentes ni a validaciones de otras sesiones. Los temporales heredados se excluyen sin borrarlos. La cancelación elimina solamente recursos propios y nunca reglas preexistentes por su antigüedad. Se pueden reintentar cancelaciones, cargas fallidas y finalizaciones parciales tras reconstruir el servicio. Los 404 esperados de grafos ausentes se distinguen de fallos de infraestructura. Una sesión completada responde 409 al intentar cancelarla y conserva su módulo; un error operacional de limpieza responde 503, sin fingir que completó. La UI conserva el ID tras fallos, evita dobles acciones, recupera sesiones y mantiene visible una incorporación completada con limpieza pendiente hasta confirmarla.

REP-04. Las respuestas de lista, detalle, creación y actualización usan un DTO sin password y con hasPassword. El secreto sólo puede entrar, no se serializa ni se incluye en toString; se redactan credenciales habituales presentes en URLs JDBC antiguas. PUT parcial conserva campos omitidos/null y contraseñas vacías; una contraseña nueva no vacía reemplaza la anterior. Un marcador de URL redactada no sobrescribe la URL almacenada. Los errores y registros propios no repiten mensajes del driver que puedan incluir credenciales. La UI limpia el secreto al cerrar el formulario y no requiere leer el valor guardado.

3. ESQUEMA, ALCANCE Y LÍMITES
Se agrega standard_incorporation_sessions y una columna nullable/unique incorporation_session_id en ontology_modules. Se conserva la configuración existente ddl-auto:update. Un despliegue con esquema administrado necesita incorporar esos cambios por su proceso normal. H2 es dependencia exclusiva de pruebas; no se actualizó el stack de producción.
El aislamiento de mutaciones se verifica para una instancia de backend, con persistencia de checkpoints. No se declara coordinación entre varias réplicas. La propiedad es recurso-sesión, dentro del modelo de acceso existente.
La compensación ERP no equivale a una transacción distribuida: un crash no ejecuta callbacks, el snapshot es de memoria, el resultado de commit puede ser desconocido y Fuseki puede impedir la recuperación. La comparación por contenido tampoco identifica a un escritor que haya publicado exactamente las mismas triples. Los casos no confirmados quedan registrados para reconciliación; no se declara restauración universal.
No se ejecutó un despliegue sobre la base PostgreSQL del usuario ni una aceptación completa en navegador con servicios reales. Las pruebas de UI usan API simulada; los contratos HTTP de backend se verifican con MockMvc. No se publicaron cambios ni se repitieron las 120 mediciones científicas.
El adaptador SQL sigue siendo un demostrador limitado. Este trabajo no agrega R2RML general, autenticación ni cifrado de secretos en reposo. Los P2/P3 del backlog original permanecen fuera de esta implementación, incluidos formatos RDF y conteos del Wizard. Las decisiones científicas siguen separadas para Marcela.
